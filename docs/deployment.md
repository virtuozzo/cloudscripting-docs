# Artifact deployment

Deployment uses a validated immutable artifact and an observed hosting contract. The current contract keeps deployment disabled until the actual host, backup and restore requirements are confirmed.

Run local tooling from the Devbox shell after `uv sync --locked`, as described in [contributor setup](../README.md#contributor-setup). The delivery shell wrappers use `uv run --locked` by default; an explicit `PYTHON` path selects an already prepared interpreter for controlled tests or automation. CI uses the pinned uv version and committed lockfile. The remote host still needs only the Python standard library for its transaction helper.

`hugo-check.yml` has no deployment secrets and runs fixtures/current-content checks on Linux, where exact-case Git exports are possible. `build-release.yml` is manually dispatched, builds the complete root plus retained release artifact, validates it and packages it once. Its summary distinguishes the GitHub artifact ID/digest from the inner archive SHA-256. The archive contains `site/`, `artifact.json`, `checksums.sha256` and `validation/`; only `site/` is served. Current root and explicit latest remain independent build identities.

Both manually dispatched deployment workflows take the successful build run ID, exact artifact ID and accepted archive SHA-256. They check the repository, successful manual release run, API workflow ID/path, exact artifact/run relationship and matching full run/artifact head SHA. The archive tooling commit must equal that trusted head SHA. They download the same bytes and verify complete retained prefixes, provenance and offline validation before configuring transport. Self-consistent PR artifacts cannot bypass these source gates. Production additionally requires a private staging acceptance reference for that exact archive SHA-256. They do not rebuild, pull theme/source branches, commit, or change artifact URLs. Promotion uses the production-URL archive on staging, with host isolation and the mapping required by the staging runbook.

## Confirmed operational configuration

`migration/hosting-contract.yaml` remains the durable source of host facts and evidence. The separate private operational JSON in `DEPLOY_HOST_CONFIG` transcribes endpoint/path/inventory values for execution; its `hosting_contract_sha256` must match the exact reviewed canonical contract file in the workflow checkout. An operational record cannot point to an alternate contract file. It cannot turn an incomplete hosting contract into acceptance: the contract must have `host_acceptance: confirmed`, `capabilities.status: observed`, and `capabilities.accepted_strategy` equal to the target strategy. If targets differ, `accepted_strategy` may map `staging` and `production` to their confirmed strategies. The target's `evidence` identifies the private owner-reviewed operational record. These fields require actual host evidence, not inferred reference paths.

Start from `scripts/deploy/host-config.example.json`. Its nulls/false declarations deliberately fail. Keep completed copies outside Git. Configure GitHub `staging` and `production` environments with `DEPLOY_HOST_CONFIG`, `SSH_KEY`, and host-owner-verified `SSH_KNOWN_HOSTS`; use environment protection according to the named deployment owner's policy. No runtime `ssh-keyscan` replaces host-key verification. The workflows never print these secrets. The operational record requires explicit managed and retired regular-file inventories as `{path, sha256}` records; an empty list is a reviewed declaration of none. Managed files must not collide with any new artifact entry or ancestor. Existing non-artifact files require a managed preservation or retired disposition. Symlink/special-file inventories require host-specific preparation outside this regular-file automation.

Paths are confirmed absolute physical paths with no spaces/control characters or symlink ancestors. Upload, release, backup, configuration snapshot and public-pointer locations must be separate. `config_snapshot_root` must be an owner-prepared complete scoped configuration snapshot/root covering the actual rewrite/TLS/maps/runtime state and its restore mapping, outside public trees; the script cannot discover completeness. The hosting owner confirms metadata preservation, write quiescence, space, symlink serving and the selected path mapping. Remote preflight verifies GNU `tar`/`cp`, case-sensitive storage, same filesystem, existing pointer identity, current regular-file hashes, managed collisions and free space before SCP. Keep writers quiesced through the entire transaction.

Two automated strategies are supported:

- `existing-symlink`: the public path must already be a symlink resolving to the exact recorded `expected_current_target`. A complete served-tree and configuration backup is archived with GNU ACL/xattr/owner preservation and compared before the switch. The former tree stays in place.
- `initial-symlink`: the public path must be confirmed absent and `expected_current_target` must be null. The script refuses any existing directory, file, dangling symlink or concurrent creation. It backs up the confirmed configuration root; there is no previous served tree at that path. The host must already map that public path and serve symlink targets. This is not automatic conversion of an existing directory.

An existing real-directory deployment needs the one-time provisioning/rehearsal described in the [staging runbook](runbooks/staging.md), or a separately accepted host-specific strategy. This limited symlink automation is not a claim that the reference server already supports it.

## Transaction and recovery

`deploy-artifact.sh staging|production ARCHIVE SHA256 MANIFEST REPORT HOST_CONFIG [TRUSTED_TOOLING_COMMIT]` validates locally, performs SSH preflight, SCPs into a newly created private upload session, and runs the transaction over SSH. Every command block is independently fail-closed. The workflows supply the trusted release-run head SHA on both local verifications. The remote script rechecks the archive digest before fresh safe extraction, verifies the exact checksum inventory, captures and compares real backups, constructs an immutable complete release, overlays only inventoried managed bytes, rechecks the live tree, then switches the pointer. It keeps archive metadata outside the public tree. No blanket rsync deletion or configuration rewrite occurs. The receipt records the archive, backup hashes, old/new pointer targets and combined served-tree hashes; HTTP/browser acceptance remains pending.

Failures before switching retain the old pointer. If an exception occurs while verifying/recording the switch, the script restores the prior pointer (or removes its own first-install pointer) when it still owns the new target. It never deletes the old tree, backups or failed candidate. Retained private upload/candidate/backup directories need deliberate operator cleanup after diagnosis, not a broad automatic deletion. A later retry of the same artifact on the same host refuses an existing immutable release directory, requiring inspection first.

After switching, the operator performs the [staging](runbooks/staging.md) and [production](runbooks/production.md) acceptance checks. Rehearse and execute [rollback](runbooks/rollback.md) to restore the previous served tree and applicable configuration together. The JSON receipt is evidence and a pointer record, not a substitute for off-host recovery, ACL/xattr restore verification or a rollback rehearsal. This script does not mutate server config; changes to TLS/old-domain redirects, config tests/reloads, backups and recovery ownership remain host-runbook gates.

## Local commands and limits

```sh
set -eu
uv run --locked python -m scripts.deploy.artifact package build/artifact migration/release-sources.yaml build/delivery/cloudscripting-docs.tar.gz build/package-validation.json
bash scripts/deploy/verify-artifact.sh build/delivery/cloudscripting-docs.tar.gz ACCEPTED_SHA256 migration/release-sources.yaml build/archive-validation.json
uv run --locked python -m unittest discover -s tests/migration -p test_delivery.py
```

Full archives contain case-only image pairs. On macOS set `CS_DELIVERY_TMPDIR` to an existing case-sensitive volume for verification/packaging extraction; otherwise verification fails clearly rather than merging names. For all transaction fixtures on macOS, also set `CS_DELIVERY_TEST_TMPDIR` to such a volume. The default test run skips transaction successes when its temporary storage is case-insensitive; the case-sensitive run exercises them. Transport commands are replaced with safe local fixture tools; the actual Python transaction and shell entry points run against disposable trees. macOS also doubles GNU backup/copy tools with a regular-file model; Linux CI uses the real GNU backup/copy tools on its disposable trees. These fixtures do not verify real remote metadata, credentials, workflow execution, staging isolation or hosting acceptance. Linux CI runs the same suite, and real hosting acceptance still requires the named owner and runbooks.

CI pins action revisions and checks Hugo Extended 0.124.1 and Task 3.44.1 downloads against their recorded SHA-256 values before extraction. Tool setup is confined to runner temporary storage.
